Two trust models in one product

Sealed one-to-one chats, per-member sealed groups and readable, moderated Spaces: different promises for different places, stated plainly.

On this page

  1. Why there are two models
  2. One to one: sealed on the device
  3. What that does not prove
  4. Delivery and sync
  5. Groups: sealed per member
  6. Spaces, communities and channels
  7. Media
  8. Calls

01Why there are two models

A private conversation and a moderated community need opposite things. A private chat should be unreadable to the service. A community needs moderation, and moderation needs the service to see content. Lagoon keeps both and does not blur them.

Space messages are readable on the service so they can be moderated. They are not end-to-end encrypted, and the product should never imply that they are.

02One to one: sealed on the device

A dedicated module uses the browser's cryptographic APIs: ECDH on P-256 for key agreement, HKDF with SHA-256 and HMAC-based derivation, and AES-GCM for encryption. Device keys live in IndexedDB. Public keys and prekeys are published, and the module handles session state, safety codes, encrypted files, and encrypted key backup and restore. It also contains ratchet-related logic and a prekey handshake.

The service stores message records in D1, but the client is built so that it receives sealed content rather than readable private text. This is a substantial implementation, not an encryption icon.

03What that does not prove

Cryptographic code is not an audit. The protocol has not been independently reviewed, and strong security guarantees should wait until it has been.

04Delivery and sync

The live path covers phone-number account lookup, sending, synchronization, delivery acknowledgements, history and live events over WebSockets. A per-user Inbox object holds the connections and delivers events.

05Groups: sealed per member

For groups, the sending device seals each message separately for each member. The server keeps membership and roles and relays the encrypted envelopes. The backend covers creation, invitations, joining and leaving, member management, roles, editing, sync, delivery acknowledgements, read state, reports and moderation workflows.

Group encryption should not automatically be credited with every property of the one-to-one protocol.

06Spaces, communities and channels

Spaces are invite-based environments with members, roles, text channels, channel permissions, reports, moderation, automated moderation rules, adult-channel restrictions and invite management. Communities are named groups with membership and an announcement feed controlled by owners and administrators.

Channels are one-to-many broadcasting: creation, a directory, following, posts, reactions, polls, reports and deletion. Followers pull the feed instead of the system pushing to each of them.

07Media

Images, video, voice messages, documents and view-once media are uploaded in chunks, kept locally in IndexedDB and fetched on demand. The backend stores the chunks in D1 rather than in object storage. The limits in code are 384 KB per chunk, 25 MB per file and 200 MB of uploads per person per day.

That reduces infrastructure for now, but database-backed media deserves a dedicated scaling review.

08Calls

There are two call paths: a simulated local experience and a live WebRTC implementation. The server handles signalling, call logs and ICE configuration while audio and video travel peer to peer. The live path is for individual calls. Group-call screens that exist in the simulated experience should not be presented as a finished live feature.

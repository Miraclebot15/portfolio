Lagoon, end to end

A social operating system built from a modular frontend and a real edge backend, with an honest map of what is live and what is simulated.

01What Lagoon is trying to be

Lagoon is a social operating system built around communication, relationships, content, communities, information and personal productivity. It is not meant to be another feed-first network. The direction is relationship-oriented rather than engagement-oriented: connect people, their conversations, their interests and what they want to get done.

The idea is one environment where people can communicate privately, keep relationships and communities, share media, discover information, read, watch, learn and create, organize their conversations and activities, and use an integrated assistant. Communication is the foundation, but it is not the limit.

02A frontend built from registered modules

The frontend is custom modular JavaScript, not a React or Next.js application. Numbered modules share one application namespace with common state, an event bus, feature registries, navigation and screen management, shared interface components, a shell and theme system, and a boot layer.

Features plug in through small registration calls for tabs, screens, attachments, settings, message types, chat actions, quick actions and shells, instead of being written into one enormous file. That gives Lagoon a plugin-like internal structure without a separate package per feature.

03A build step that enforces rules

A build script collects the CSS and JavaScript from the source folder, sorts modules by filename, merges the CSS, keeps each JavaScript file as its own script tag so a syntax error stays isolated to one module, checks syntax, rejects em dashes and en dashes, and emits a self-contained HTML app.

One caution: older flat files sit beside the source folder as a parallel layout. Only the source folder is built, so the two must not be treated as interchangeable.

04A backend on the edge

Cloudflare Workers handle the HTTP requests. D1 holds the relational data, Durable Objects hold live connections and shared counters, server-side AI runs on the same platform, and a separate hosted service executes remote code. An Inbox object manages one user's active WebSocket connections and event delivery.

An older room object is explicitly retired and answers with HTTP 410. Lagoon should not be described as having a room-based messaging service.

05Local first, live when signed in

The app works locally with simulated conversations, messages, status changes and persistence. When a user signs in, selected features are replaced or extended by real services. So not every screen is a live capability: some are simulated, some live, some both, and some are in test mode.

Keeping demo state and live state strictly separate is a design rule, and the main thing the next stage should consolidate.

06Shells, not skins

There are 25 shells, from Glass, Material and Bento to Editorial, Swiss, Terminal and two iOS variants. A shell is not a color preset. It can change navigation, layout, component shapes, typography, density, motion, light and dark themes, chat bubbles, lists, sheets, cards and responsive behavior. One feature implementation inherits every treatment without being rewritten.

07How it is checked

Browser tests run at phone, tablet and desktop sizes and collect page and console errors, screenshots, shell audits, overflow and contrast checks and feature tests, across 36 frontend test files. Nine backend scripts cover authentication and general API behavior, messaging, WebSocket delivery, avatars, the assistant, code execution, public data adapters, privacy and social features. Some target the live API and others run against isolated local environments.

Honest limits: the existence of tests is not the same as passing them, and a code review is not a fresh run of the suite. The package's default test command is also a placeholder, so no single command runs everything yet.

NEXUS CORE, end to end

How a request moves through a governance-first agent prototype: what is real, what is simulated and what is still planned.

01The principle, and the status

NEXUS CORE treats a language model as an untrusted, probabilistic engine. The model can interpret a request, choose an approach, propose tool calls and revise a rejected plan. It cannot authorize its own proposal: every plan passes through a deterministic, fail-closed policy check before anything executes.

This note describes the current working prototype. It is a governance-first orchestration pipeline in active development, not a finished sandbox or a production-ready autonomous platform. Where something is simulated or only planned, the note says so.

02The layers

The interface is a Next.js and React Command Center where users submit tasks, inspect conversations, watch pipeline events and review governance decisions. It reads a Server-Sent Events stream, so blocked decisions and the correction loop are visible instead of hidden behind a single answer.

A FastAPI backend exposes authentication, projects, conversations, messages, task streaming, artifacts and audit records. It validates request bodies, resolves who is calling and hands orchestration to one orchestrator. A demo identity exists for development. It is not an acceptable default for a multi-user deployment.

Before planning, the orchestrator passes up to the last 20 messages to a semantic understanding step that infers intent, task type, complexity, ambiguity and security signals, with a fallback if the model is unavailable. A separate pattern classifier checks the original input for instruction overrides, prompt extraction, fake system messages and obfuscation. These signals inform the plan and add defense in depth. They are evidence, not authorization.

A router maps the task to a category, model configuration and reasoning mode, using semantic hints with a keyword fallback. The planner agent, ELLA, then turns the request into a structured execution plan: a summary, a response mode and ordered steps, each with an action, a target, parameters and a rationale.

Governance evaluates that plan. If it is blocked, a correction agent, JANE, may revise it. Approved plans reach the execution layer, which dispatches supported actions and collects logs and artifacts. SQLite stores projects, conversations, messages, tasks, artifacts and the audit records.

03Life of a request

A request starts in the frontend and opens a streaming endpoint. The orchestrator creates a task record, loads earlier messages and stores the new user message. Semantic understanding and the security classifier run, the router picks a category, and the planner proposes a structured plan that is parsed and validated against a shared schema.

Governance then evaluates the plan independently of the planner. A blocked plan may go to the correction agent, and the revised plan must pass governance again. Repeated rejection ends the task. An approved plan is executed, results and artifacts are collected, and the response and task state are saved. Each stage is streamed to the client as it completes and written to the audit record.

One honest edge: when a client disconnects, the pipeline stops advancing, but a model request that is already in flight cannot be guaranteed to stop immediately.

04A plan that parses is not a plan that is safe

Model output goes through defensive JSON extraction and schema validation before it becomes a plan. That establishes structure only. A well-formed plan can still ask for something dangerous, which is why validation and authorization are separate steps.

The planner also has three response modes: answer directly, ask for clarification without inventing steps, or execute tools. The distinction keeps a vague request from being turned into confident-looking actions.

05Governance fails closed

The governance layer is plain Python rules, not another model asked whether the plan seems safe. It inspects the flattened content of each step for dangerous system commands, destructive SQL, sensitive file paths, path traversal and secret exfiltration, and it rejects blocked action names. The result is a structured verdict: the decision, the rules that fired, the security signals and a reason.

If evaluation itself throws an exception, the verdict is blocked, never implicit approval. The same input and configuration give the same decision, and a rejection always names its reason.

The limit matters just as much: a pattern-based evaluator is only as complete as its patterns. It is not a full policy language and not proof of safety.

06Correction is not an override

When a plan is blocked, the correction agent receives the rejected plan and the governance feedback and tries again. Its output is more model-generated data, so it is parsed, validated and evaluated exactly like the original. Without that rule, the correction path would be a bypass around the policy boundary.

The loop is bounded, with a default maximum of two correction attempts, so a stubborn plan ends in rejection instead of retrying forever. It does not provide human approval, rollback or protection against partial effects from future real integrations.

07What is simulated, and why it matters

Most actions in the prototype are simulated. Read-only web search is the one documented real external tool. Importing a tool module does not mean its action has a production-safe execution path.

The distinction matters because a simulated file write shows orchestration behavior. It does not prove filesystem isolation, and a governance verdict is not a replacement for a separate permission check at the real tool boundary. The code also sanitizes search results and classifies known injection patterns. Those are supporting defenses, not proof that hostile content is neutralized.

08An audit trail with honest limits

Each stage writes an append-oriented audit record: the task, stage, label, details, a timestamp, the previous record's hash and its own SHA-256 hash. The event stream carries the record hash, so the interface can show a hash-linked timeline and whether the chain verifies. Deleting a conversation or a message does not touch the audit tables, so the execution history can outlive the content.

Hash linking detects some kinds of tampering. It does not make the database immutable, because someone who can rewrite the records can recompute the chain. Stronger integrity would need independent checkpoints or signatures.

09A bug worth telling: timestamps that sort wrong

Timestamps were stored as text, and Python's default ISO format drops the fractional seconds when the microseconds are exactly zero. Mixed representations then sort and compare unexpectedly as strings. That affects message order and any operation that deletes a message and everything after it.

The fix is to always serialize with explicit microsecond precision, so every stored timestamp has the same shape and text order matches time order. No separate regression test for this is claimed yet.

10Built, and not yet

Built in the prototype: the API and Command Center, structured plans with shared schemas, semantic understanding and prompt classification, routing, the planner and correction agents, fail-closed governance, bounded correction with re-evaluation, SSE pipeline events, SQLite persistence, hash-linked audit records with chain verification, multi-turn context, full-text message search where the SQLite runtime supports it, and mostly simulated execution with one real read-only search path.

Still planned or incomplete: enforced production authentication with verified isolation between users, authorization enforced at each real tool boundary, a general human-approval workflow, real integrations with scoped permissions, complete automated security and regression tests, independent audit checkpoints, rate limiting and monitoring, and embedding-based memory in place of today's full-text search.

11What comes next

The first priority is making authorization an execution invariant: a typed contract between governance and execution, so every real tool call traces back to the exact approved action, target and parameters, and anything unknown or malformed is rejected by default.

After that come reproducible security tests that record false positives and false negatives, lifecycle failure tests for timeouts, disconnects and corrupted audit chains, one narrowly scoped real integration with every allowed, blocked, denied and failed path tested, signed audit checkpoints, and reliability baselines before any scaling decisions. The longer plan is in the next note.

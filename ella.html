About

ELLA is a conversational assistant built for WhatsApp. It models a chat as ordered context, not as isolated commands, and routes each message to a handler based on intent and conversation state. It is designed for individual and group chats and for the way people actually write: fragments, abbreviations, Nigerian English and Pidgin.

The engineering emphasis is on routing correctness and honest failure. A message that merely resembles a command should not run it, an ambiguous reference should produce a question, and an operation should be reported as complete only when it completed.

What it’s for

  • Maintains conversation context across individual and group chats.
  • Routes messages by intent and state, so partial keyword matches do not trigger specialized handlers.
  • Asks a short clarifying question when a reference is ambiguous, instead of guessing.
  • Understands Nigerian English and Pidgin as part of routing, not only tone.
  • Reports provider and integration failures as failures.
  • Keeps developer and administrative controls separate from the user-facing surface.

How a message is handled

Open a step to read its role and the failure it guards against.

  1. An event from an individual or group chat, with sender and chat metadata. Treated as untrusted text.

  2. Recent conversation state used to resolve references, group addressing and language.

  3. Chooses a handler from intent and context. Ambiguity produces a clarifying question, not a guess.

  4. A specialized handler, or a general model-written reply when no handler fits.

  5. Sent only after the underlying operation has succeeded. Failures are reported as failures.

Engineering concerns

Design intent for a conversational assistant on a messaging platform.

  1. Messages arrive as short, out-of-order, multilingual events. Treating the conversation as ordered context lets the assistant resolve references that single-message matching cannot.

  2. Handler selection uses intent and state. Lexical overlap is weak evidence, and a false positive has an asymmetric cost because it executes behavior the user never requested.

  3. When a reference cannot be resolved, the choice is to ask or to guess. A clarifying question costs one round trip, a wrong action costs trust, so the design prefers the question when the ambiguity changes which handler runs.

  4. Groups introduce addressing and threading problems: whether the assistant is being spoken to, which message a reply refers to, and how much shared context is relevant.

  5. The assistant depends on third-party services that fail. The contract is that success is reported only on success, because a confident message about something that did not happen is worse than a plain error.

  6. Experimental work, such as voice, is maintained apart from production behavior and is not presented as available until verified. Operational controls sit behind their own interface.
